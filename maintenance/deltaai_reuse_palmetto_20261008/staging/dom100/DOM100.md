## Profiling and pilots

After preparation succeeds, submit separate profiling allocations:

```bash
sbatch --constraint=gpu_a100_40gb slurm/profile_dom100_a100.sbatch
sbatch --constraint=gpu_a100_80gb slurm/profile_dom100_a100.sbatch
sbatch slurm/profile_dom100_h100.sbatch
sbatch slurm/profile_dom100_h200.sbatch
```

Each campaign isolates trials in fresh processes. It benchmarks FP32/BF16 and
the divisors of 352, allocates real optimizer states during warmup, then measures
real decoded data with worker/prefetch/sampler variants and fused AdamW. Model
computation, end-to-end throughput, loading wait, GPU utilization, peak GPU/RAM
use, and estimated training duration are recorded under `profiling/`. A safe
profile requires 15% GPU and host-memory headroom and verification on all six
architectures. Compilation remains off. Hardware fingerprints include device
name, memory, capability, PyTorch and CUDA versions. They cannot be reused on
an unprofiled GPU/software combination.

Choose one approved GPU class for the common tuning campaign:

```bash
sbatch slurm/pilots_dom100.sbatch
# After every pilot completes:
python scripts/dom100.py choose --family-root "$DOM100_ROOT"
sbatch slurm/smoke_dom100.sbatch
```

Use `sbatch --gpus=h100:1` or `--gpus=h200:1` to override the pilot/smoke GPU.
Only one tuning campaign selects the frozen shared recipe. Four center-rate
pilots compare both samplers on DOM/Coordinate at `3e-5`. Four additional pilots
test `1e-5` and `1e-4` using the selected sampler. Each uses the same 4,096
training episodes, 8,192 validation anchors, 2,000 optimizer updates, 1,000
warmup updates and the production cosine time scale. Validation at updates
1,500 and 2,000 determines the mean final score. Blocks require ≥10% throughput
improvement and ≤5% MSE degradation on both architectures. A diverged LR is
discarded; the best stable paired relative score wins, ties favoring lower LR.
Completed pilot weights are deleted. Production always starts from the common
pretrained weights with a fresh optimizer.

Smoke allocations execute decoded-batch backward/optimizer/inference and strict
checkpoint reload for every variant, check velocity gradients and ignore poisoned
future trajectories. Production requires a smoke result for its exact GPU
profile and the common precision. Repeat smoke tests for every production GPU
class after the recipe is frozen. A GPU class selecting a different precision
must be reprofiled at the shared precision before use, for example
`DOM100_PRECISION=bf16 sbatch slurm/profile_dom100_h100.sbatch`.

Integration replays actual absolute DOM demonstrations through the existing
robot-base pose controller. All replay cases must complete with ≤5 cm EE position
RMS difference. Euler/wxyz roundtripping and a decoded live Coordinate+velocity+
phase controller case must pass. The untrained controller smoke is required to
execute correctly; its task success is recorded rather than required.

The five-frame lookahead used by the existing label generator is preserved and
recorded; the finalized analytic chunk grid remains `k/25`. Collision sensors
measure arm/hand/finger contacts above 1 N, subtracting intentional target-object
contact on hand/finger links. Grasp is observed attachment, lift requires 2 cm,
completion/place use simulator success conditions, and drops/timeouts use the
actual termination terms. Missing collision instrumentation fails evaluation.
Assets/configs, replay arrays and the container are fingerprinted.
Attachment stability is measured in the EE frame, so rotating a securely
grasped object does not masquerade as attachment loss. Both prefix replay and
live control use the same past-only rotation-aware rule.

## Independent production and recovery

```bash
python scripts/dom100.py preflight --family-root "$DOM100_ROOT"
bash scripts/submit_dom100.sh --dry-run
bash scripts/submit_dom100.sh
# Approved class override:
DOM100_GPU=h100 bash scripts/submit_dom100.sh
```

The helper checks the frozen recipe, profiles and six decoded smoke results,
then submits the six files in order without
dependencies. A100 submissions automatically constrain VRAM when only one
memory class is approved. Jobs also validate their exact allocated hardware
when they start. Partial submission IDs are persisted; retrying the helper
does not submit duplicates. Standalone files can also be submitted individually
from the project directory. H100/H200 overrides use `sbatch --gpus=...:1`.

Each run lives in `runs/<short-name>`, owns a filesystem lock and keeps a
persistent W&B ID. Checkpoint generations contain matching weights, optimizer,
scheduler, RNG, completed epochs, consumed sample cursor, validation state,
best metadata and provenance. They are published atomically every 30 minutes,
at epoch boundaries, and on USR1/TERM at update boundaries. The last partial
effective batch is weighted by its actual sample count. Validation interrupted
by preemption resumes before the next epoch. Per-sample augmentation and
instruction randomness and a separate loader RNG make prefetch irrelevant to
the consumed cursor. The 20-minute walltime notice gives time to save. A graceful
continuation exits 75 and attempts requeue; ordinary failures are not requeued
indefinitely. Resubmitting the same standalone file resumes the existing run.

Validation anchors are evaluated every epoch over all 20 predicted/executed steps,
translation, Euler orientation, gripper and phase. Milestone checkpoints at
1, 5 and every 10 epochs preserve checkpoints and durable evaluation requests.
With this family's deferred mode, simulator evaluation waits for the separately
collected dataset after training. Evaluations use their own single-GPU allocations;
milestone/best generations are retained. The original `during_training` mode
dispatches reserved suites automatically and requires controller integration.

```bash
# Retry requests that were never submitted:
python scripts/dom_closed_loop.py dispatch --family-root "$DOM100_ROOT"
# For an evaluation job that failed, resubmit its concrete request:
sbatch slurm/evaluate_dom100.sbatch "$DOM100_ROOT" /absolute/path/to/evaluation-request.json
# Verify every completed run:
python scripts/dom100.py verify --family-root "$DOM100_ROOT" --variant dom100
# Repeat verify for kr100, domv100, krv100, krp100 and krvp100, then:
python scripts/dom_closed_loop.py complete --family-root "$DOM100_ROOT"
```

`complete` writes `comparison.json` only after all six verified 100-epoch
weights/optimizer/scheduler states, every planned validation manipulation suite,
and both reserved test evaluations exist. No loss-only result is reported as
task completion. Timing estimates exclude validation, checkpoint I/O and queue
time; measured production samples/second is reported separately.
